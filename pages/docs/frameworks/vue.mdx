# Vue

`@fluxgantt/vue` provides a `<FluxGantt>` Vue 3 component and a `useFluxGantt` composable. This
is the code from
[`examples/vue-vite-demo`](https://github.com/thai-pc/fluxgantt/tree/master/examples/vue-vite-demo).

## `<FluxGantt>`

```vue
<script setup lang="ts">
import { FluxGantt } from '@fluxgantt/vue';
import { toTaskId } from '@fluxgantt/core';
import type { Task, TaskInput, DependencyInput } from '@fluxgantt/vue';

const tasks: TaskInput[] = [
  { id: toTaskId('design'), name: 'Design', start: '2026-08-03', end: '2026-08-05', progress: 1, type: 'task' },
  { id: toTaskId('build'), name: 'Build', start: '2026-08-05', end: '2026-08-10', progress: 0.6, type: 'task' },
  { id: toTaskId('review'), name: 'Review', start: '2026-08-10', end: '2026-08-12', progress: 0, type: 'task' },
];

const dependencies: DependencyInput[] = [
  { from: toTaskId('design'), to: toTaskId('build'), type: 'FS' },
  { from: toTaskId('build'), to: toTaskId('review'), type: 'FS' },
];

// The template emit surfaces `prevStart` as `unknown` (Vue widens emit payload types).
function onTaskMoved(task: Task, prevStart: unknown) {
  console.log(`${task.name} moved from ${prevStart}`);
}
</script>

<template>
  <FluxGantt
    :tasks="tasks"
    :dependencies="dependencies"
    style="height: 420px"
    @task-moved="onTaskMoved"
  />
</template>
```

## Props

`FluxGanttProps` mirrors the engine's `GanttConfig` one-to-one: `tasks`, `dependencies`,
`calendar`, `viewMode`, `density`, `locale`, `ariaLabel`, `messages`, `theme`, `canvasViewportHeight`, `readOnly`,
`enableDependencyDrag`, `schedulingMode`, `historyLimit`, `initialCollapsed`, `rollup`, `rtl`, and the `onTaskChange` catch-all. In a template you bind them kebab- or camelCase (`:tasks`,
`:view-mode`).

Like React, these are **construction-time only** (read once), except `theme`, which is reactive (applied via
`setTheme`) and defaults to `'light'` rather than core's `'auto'` — pass `theme="auto"` to follow the OS. To change `viewMode` after mount,
force a remount with `:key`. (`onTaskChange` is also read at call time, so it stays current.) The `theme` prop is validated (`'light'`, `'dark'` or `'auto'`).

**Behavior change for `aria-label`:** `aria-label="Plan"` (or `:aria-label`) now binds to the `ariaLabel` prop and names the chart's `<svg>`; before, it fell through to the root `<div>`. Update any CSS or test selector that matched `[aria-label]` on the container.

To remount:

```vue
<FluxGantt :key="viewMode" :view-mode="viewMode" :tasks="tasks" />
```

### `class` / `style`

`class` and `style` are **not** declared props — Vue's attribute fallthrough merges them onto
the component's root `<div>` automatically. So `style="height: 420px"` above just works; don't
look for a `style` prop in the type.

## Emits

The component emits one kebab-case event per engine event. Listen with `@`:

| Emit | Payload |
|---|---|
| `@task-added` | `(task)` |
| `@task-moved` | `(task, prevStart)` |
| `@task-resized` | `(task, prevDuration)` |
| `@task-progressed` | `(task, prevProgress)` |
| `@task-removed` | `(taskId)` |
| `@task-updated` | `(payload)` — **experimental** (`@beta`), see below |
| `@dependency-added` | `(dependency)` |
| `@dependency-removed` | `(dependencyId)` |
| `@critical-path-computed` | `(criticalTaskIds)` |

Note the events are kebab-case (`@task-moved`, not `@taskMoved`).

`@task-updated` is **experimental** (`@beta`): it may change in any minor release (see
[Stability](/docs/stability)). It bridges core's [`task:updated`](/docs/api#taskupdated-experimental)
event and receives its `TaskUpdatedPayload` (`taskId`, `task`, `prev`, `changed`, and `source` for
undo/redo), which `@fluxgantt/vue` re-exports. It is emitted for every field-level change of an
existing task, after `@task-moved` / `@task-resized` / `@task-progressed` and after `onTaskChange`,
so listen to it **instead of** those, not alongside them:

```vue
<script setup lang="ts">
import type { TaskUpdatedPayload } from '@fluxgantt/vue';

function onTaskUpdated({ taskId, changed, source }: TaskUpdatedPayload) {
  if (source) return; // undo/redo replay
  console.log(`${taskId} changed: ${changed.join(', ')}`);
}
</script>

<template>
  <FluxGantt :tasks="tasks" @task-updated="onTaskUpdated" />
</template>
```

## Template ref → the instance

`<FluxGantt ref>` exposes the full `GanttInstance` (every method, pre-bound), so a template ref
drives it imperatively:

```vue
<script setup lang="ts">
import { ref } from 'vue';
import { FluxGantt } from '@fluxgantt/vue';
import type { FluxGanttRef } from '@fluxgantt/vue';
import { toTaskId } from '@fluxgantt/core';

const gantt = ref<FluxGanttRef>();

function addQa() {
  gantt.value?.addTask({
    id: toTaskId('qa'), name: 'QA', start: '2026-08-12', end: '2026-08-13', progress: 0, type: 'task',
  });
}
</script>

<template>
  <button @click="addQa">Add task</button>
  <FluxGantt ref="gantt" :tasks="tasks" :dependencies="dependencies" />
</template>
```

## The `useFluxGantt` composable

```ts
import { useFluxGantt } from '@fluxgantt/vue';

const { containerRef, instance } = useFluxGantt({ tasks, dependencies });
// bind containerRef to a <div ref="containerRef">; instance is the full GanttInstance.
```

## Grid columns and cell editing

:::warning
**Experimental.** The grid entries are `@beta`, like the [core grid](/docs/concepts/grid-columns)
they wrap (since `@fluxgantt/vue` 0.6.0). They may change in any minor release.
:::

Two opt-in entries bring the grid to Vue. A chart that imports neither ships no grid code; the
default `@fluxgantt/vue` entry, its props, emits and types are unchanged.

| Entry | Exports | Composes |
|---|---|---|
| `@fluxgantt/vue/grid` | `FluxGanttGrid`, `useFluxGanttGrid` | `<FluxGantt>` + [`withGrid`](/docs/concepts/grid-columns) |
| `@fluxgantt/vue/grid-editing` | `FluxGanttGridEditing`, `useFluxGanttGridEditing` | the above + [`withGridEditing`](/docs/interactions/editing-cells), after `withGrid` (`withRtl` stays last) |

Both also re-export the grid types (`GridColumnInput`, `GridOptions`, `ColumnResizedPayload`,
`CellEditor`, and, from `/grid-editing`, `GridEditingOptions`, `CellEditRequestedPayload`, ...).

```vue
<script setup lang="ts">
import { FluxGanttGridEditing, type GridColumnInput } from '@fluxgantt/vue/grid-editing';
import type { CellEditRequestedPayload, ColumnResizedPayload, GridEditingOptions } from '@fluxgantt/vue/grid-editing';

// The library never persists widths: read them back and pass them as `width`.
const saved = loadWidths(); // Record<string, number>, validated

// Defined once in setup (or at module scope): the column functions keep a stable identity.
const columns: GridColumnInput[] = [
  { id: 'name', ...(saved.name ? { width: saved.name } : {}) },
  { id: 'start' },
  { id: 'end' },
  {
    id: 'owner',
    header: 'Owner',
    value: (task) => (typeof task.meta?.owner === 'string' ? task.meta.owner : ''),
    ...(saved.owner ? { width: saved.owner } : {}),
  },
];
const gridEditing: GridEditingOptions = { isEditable: (task) => task.meta?.locked !== true };

function onColumnResized({ widths }: ColumnResizedPayload) {
  saveWidths(widths);
}
function onCellEditRequested(e: CellEditRequestedPayload) {
  if (e.columnId !== 'owner') return;
  e.preventDefault(); // synchronously: open YOUR editor instead of the built-in one
  openOwnerPicker(e.taskId, e.clientX, e.clientY);
}
</script>

<template>
  <FluxGanttGridEditing
    :tasks="tasks"
    :grid-columns="columns"
    :grid-options="{ durationUnit: 'days', collapseBelow: 480 }"
    :grid-editing="gridEditing"
    style="height: 420px"
    @column-resized="onColumnResized"
    @cell-edit-requested="onCellEditRequested"
  />
</template>
```

### Props and emits

| Prop / emit | Entry | Notes |
|---|---|---|
| `gridColumns` (`:grid-columns`) | both | `readonly GridColumnInput[]`. Read at creation; a later change (a new array, a replaced `ref`, or an in-place edit of a reactive array) is applied with `setGridColumns` (see below). Invalid columns throw a `RangeError` (at creation, wrapped in the usual "invalid initial config" error). |
| `gridOptions` (`:grid-options`) | both | `collapseBelow`, `durationUnit`, `resizable`. **Construction-time only.** |
| `@column-resized` | both | `(payload: ColumnResizedPayload)` |
| `gridEditing` (`:grid-editing`) | `/grid-editing` | `isEditable`, `beforeCommit`, `activate`, `commitOnBlur` ([options](/docs/interactions/editing-cells#composition-order)). `activate` and `commitOnBlur` are **construction-time only**; `isEditable` and `beforeCommit` follow the latest prop, provided they were set on the first render. |
| `@cell-edit-requested` | `/grid-editing` | `(payload: CellEditRequestedPayload)`. Call `payload.preventDefault()` synchronously to replace the built-in editor; the wrapper forwards the event synchronously, so it works from a template listener. |

Every `<FluxGantt>` prop and emit works as before, and `@task-activated` /
`@task-context-requested` report `part: 'cell'` and `columnId` on grid cells. Changing a
construction-time option (or adding `isEditable` / `beforeCommit` after the first render) is
ignored and logs **one** dev warning; change `:key` to remount.

### The exposed instance

The template ref is the full instance, typed `FluxGanttGridRef` / `FluxGanttGridEditingRef`. On top
of `FluxGanttRef` it carries `getGridColumns`, `setGridColumns`, `resizeGridColumn` and
`exportGridCsv`, and with editing `startCellEdit`, `cancelCellEdit` and `isEditingCell`:

```vue
<script setup lang="ts">
import { ref } from 'vue';
import { FluxGanttGridEditing, type FluxGanttGridEditingRef } from '@fluxgantt/vue/grid-editing';
import { toTaskId } from '@fluxgantt/core';

const gantt = ref<FluxGanttGridEditingRef>();
</script>

<template>
  <button @click="gantt?.startCellEdit(toTaskId('build'), 'name')">Rename "Build"</button>
  <FluxGanttGridEditing ref="gantt" :tasks="tasks" :grid-columns="columns" />
</template>
```

`useFluxGanttGrid(config)` and `useFluxGanttGridEditing(config)` return `{ containerRef, instance }`,
like [`useFluxGantt`](#the-usefluxgantt-composable).

### Column changes and widths

- **Columns are compared structurally**: ids, widths, headers, bounds, alignment, and the identity
  of the `value`, `format` and `editor` functions. When they differ, the wrapper calls
  `setGridColumns` (one repaint, **never a remount**). An equal array is a no-op.
- **Keep the function identities stable.** Define the column functions once, in `setup` or at
  module scope, never inline in a template expression. A new function identity on every change
  re-applies the columns (and repaints the grid) each time, holds back an open editor, and logs one
  dev warning per component.
- **User-resized widths survive re-renders.** A re-apply keeps the live width of every column
  whose declared `width` did not change, so re-passing the same columns never resets a user
  resize. To reset widths: change the declared `width`s, call `setGridColumns(...)` on the exposed
  instance, or change `:key`.
- **Persist widths yourself**: save `payload.widths` from `@column-resized` and pass them back as
  `width` ([recipe](/docs/concepts/grid-columns#persisting-widths)).
- **A re-apply waits while a cell is being edited**, and happens once when the edit ends, so an
  open editor and its text are never lost.

## Production builds

The dev-only warnings (`tasks` / `dependencies` changed identity, a construction-time grid option
changed, unstable column functions) are guarded by a bare `process.env.NODE_ENV !== 'production'`
check, which your bundler replaces (Vite and esbuild `define`, webpack `DefinePlugin`). Since
`@fluxgantt/vue` 0.6.0 a production build therefore strips them, text included, from the default
entry as well as the grid entries. Before 0.6.0 the check was written so that a browser bundle
evaluated it as "development" and shipped the warnings. An unbundled load without a `process`
global logs no warnings.

## Nuxt / SSR

`<FluxGantt>` mounts into a real DOM node, so it renders nothing meaningful during SSR. Under
Nuxt, wrap it in `<ClientOnly>`:

```vue
<ClientOnly>
  <FluxGantt :tasks="tasks" :dependencies="dependencies" />
</ClientOnly>
```

(The example app uses plain Vite — an SPA with no SSR step — so it needs no `<ClientOnly>`.)
